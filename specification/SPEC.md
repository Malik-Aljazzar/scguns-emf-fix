## Resolved: ScorchedGuns' EMF compat dead on EMF 3.x (1.1.0)

History: built 2026-10-23, briefly removed 2026-10-24 while the pack tried *Nighty's Scorched Guns Animation Compat* 1.8.0 (forces the vanilla player model via `EMFAnimationApi.registerVanillaModelCondition` whenever a gun is held, which made this bridge dead code), then restored the same day after Nighty's mod was dropped from the pack. Nighty's mod also had an uncached per-call reflection gun check (`getClass().getMethod(...)`, throwing `NoSuchMethodException` for every non-living EMF entity), so it is not a drop-in alternative.

- **Symptom**: first-person gun arms rotated/offset against the gun model, only with EMF/ETF + Fresh Animations (specifically the FA+Player add-on, whose `a_player_firstperson.jpm` drives `is_first_person_hand` arm sway/equip/jump offsets).
- **Root cause (javap against the deployed jars, not guessed)**: `OptionalClientCompat.isEntityModelFeaturesLoaded()` returns `isClassPresent("traben.entity_model_features.EMFAnimationApi") && isClassPresent("traben.entity_model_features.models.animation.EMFAnimationEntityContext")`. EMF 3.3.12 still has `EMFAnimationApi` but no `EMFAnimationEntityContext` (replaced by render states, `traben.entity_model_features.models.animation.state.*`). So it returns false, which disables: `renderCleanFirstPersonArm` (called by `RenderUtil.renderFirstPersonArm`; renders the arm from a freshly baked vanilla `PlayerModel` mesh instead of the EMF-animated one), `registerEntityModelFeaturesVariables` (`scguns:is_scguns_gun_held`), and makes `EMFModelPartRootMixin` (third-person gun pose re-applied at TAIL of `EMFModelPartRoot.animate()`) a no-op because its context reads fall back to false/null.
- **EMF 3 equivalents (verified in 3.3.12)**: `EMFAnimationEntityContext.isFirstPersonHand` -> `EMFState.state()` (nullable) `.isFirstPersonHand()`; `EMFAnimationEntityContext.getEMFEntity()` -> `EMFAnimationApi.getCurrentEntity()` (public API, null-safe; EMF's `MixinEntity` implements `EMFEntity` on `Entity`, so `instanceof Player` still works). `registerSingletonAnimationVariable(String,String,String,BooleanSupplier)` still exists, and `EMFModelPartRoot.animate()` + `allVanillaParts` (now `Map<String, EMFModelPartVanilla>`, still `ModelPart` subclasses, same erased descriptor) still match ScorchedGuns' FA mixin.
- **Fix**: port `emf.EmfAnimationContext` + resolver `emf.EmfAnimationContexts` (legacy class present -> no bridge; EMF 3 classes present -> `emf.adapter.Emf3AnimationContext`; else none) + `mixin.OptionalClientCompatEmf3BridgeMixin`: redirects the `isClassPresent` calls in `isEntityModelFeaturesLoaded()` to also count the legacy class as present when a bridge exists, and HEAD-cancels the three context reads with the bridge's answers (logic of `isScorchedGunHeldByEntityModelFeaturesContext` mirrored exactly). EMF compiled against as `compileOnly` (vendored in `libs/`, like ScorchedGuns); the adapter class only loads after detection. `LinkageError` in the adapter -> bridge permanently disabled with one warning, ScorchedGuns' own fallback values returned.

## Resolved this pass

- **Severe FPS drops (60 → 10) scaling with on-screen entity count, root-caused via spark profiler**, not a generic "too many mods" issue. Captured two separate `/sparkc profiler start --thread "Render thread"` profiles (raw `.sparkprofile` protobuf, parsed with a schema-less recursive wire-format decoder since no official proto schema was available - string/varint fields decode fine without it, confirmed by cross-referencing known class/method name patterns against real stack traces already seen in this project's crash reports). Both profiles independently surfaced the same hot pattern: `java.lang.Class#forName` + Mixin's own class-transform chain appearing dozens of times within a single short render-thread sample window - abnormal for steady-state gameplay, since classes should only ever load once.
  - **First confirmed culprit: FancyMenu.** `de.keksuccino.fancymenu.customization.screen.identifier.UniversalScreenIdentifierRegistry#getUniversalIdentifierFor` called `Class.forName(...)` on every `EventBus#post` dispatch it hooked into, uncached. Disabling FancyMenu removed all `fancymenu`/most `Class.forName` hits from a follow-up profile, but the 60→10 FPS drops persisted when looking at crowds of villagers specifically - meaning FancyMenu was a real, independent bug, but not THE bug the user was chasing.
  - **Second (the actual) culprit: ScorchedGuns.** A third profile, captured specifically while looking at a villager crowd, still showed `Class.forName` with FancyMenu confirmed absent (0 hits). Traced the call site: `top.ribs.scguns.client.compat.OptionalClientCompat#isEntityModelFeaturesFirstPersonHand`, invoked from EMF's own `EMFModelPartRoot.handler$laa000$scguns$reapplyGunPoseAfterEntityModelFeatures` hook - this exact stack trace had already been seen once before in this project, in an unrelated `ModernFix integrated server watchdog` thread-dump crash report from weeks earlier (`AdvancedDisplayTarget`-adjacent investigation), independently corroborating the finding.
  - **Verified against the real deployed `ScorchedGuns-1.5.jar` bytecode** (`javap -p -c`, not guessed): `OptionalClientCompat` has a `private static java.lang.Boolean entityModelFeaturesLoaded` cache field and a correctly-caching `isEntityModelFeaturesLoaded()` method (checks the cache, only resolves via `isClassPresent` once) - proving the mod's author *does* know the caching pattern. But three OTHER methods in the same class - `isEntityModelFeaturesFirstPersonHand()`, `getEntityModelFeaturesContextEntity()`, and `isScorchedGunHeldByEntityModelFeaturesContext()` - each independently redo a full `Class.forName("traben.entity_model_features.models.animation.EMFAnimationEntityContext", false, loader)` plus a reflective `Field`/`Method` lookup (`getField("isFirstPersonHand")` or `getMethod("getEMFEntity")`) on *every single call*, with zero caching. `isEntityModelFeaturesFirstPersonHand()` is the hot one in practice (runs per-model-part, per-entity, per-frame via the EMF hook above), but all three are the same class of bug, so all three got fixed, not just the one that happened to show up in the profile (per the project's own "robust over minimal, fix the whole class of a bug" standard).
  - **Fix**: new standalone client-only mod (`scguns_emf_fix`, this project). Rather than reimplementing the three methods' logic (which would need to call ScorchedGuns' own `private static` helpers - `isScorchedGunHeldByPlayer`/`isScorchedGunHeldByLocalPlayer` - not directly callable from outside the class), used `@Redirect` on exactly the three expensive reflective call sites (`Class.forName`, `Class.getField`, `Class.getMethod`), leaving every other instruction in all three original methods - the `instanceof` check, the actual `invoke`, the exception table, the non-EMF fallback paths - completely untouched. A failed lookup (EMF's class/member genuinely absent) is cached too, by re-throwing the same cached exception instance on every subsequent call, so a permanently-missing EMF install doesn't retry the expensive failing lookup every frame either - this preserves the original's exact exception-driven fallback behaviour (silently returns `false`/`null`), just without redoing the reflection work after the first call.
  - **Verified live**: after disabling ScorchedGuns, a profile showed 0 `scguns`/`forName`/`fancymenu` hits and the user confirmed the FPS drops were gone entirely - confirming root cause before writing any fix code, not guessing from the profile alone.
